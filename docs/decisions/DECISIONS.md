## ADR-007 Bitemporal storage — Accepted

Supersedes the object-store row of ADR-002 and the MinIO entry in ADR-003.

- **Decision:** run `pgsty/silo` locally, pinned to a release tag (initially `RELEASE.2026-09-16T00-00-00Z`). Silo is a maintained MinIO fork that keeps the S3 API, the `MINIO_*` variables, the health routes and the on-disk format, so `.env.example` (`S3_*`) is unchanged.

- **License:** AGPLv3. It runs unmodified as a local service in a personal tool and is not distributed.

## ADR-012 Knowledge time vs system time — Accepted (2026-10-05, approved by Steven)
Refines ADR-007, which did not define what `known_at` is compared with.
- **Two clocks:**
  - `as_of(known_at, effective_at=None, system_time=None)` keeps rows with `published_at <= known_at`. That is world knowledge time: when the information became public, such as an SEC acceptance datetime or an ALFRED `realtime_start`.
  - It also keeps only rows visible at `system_time` (`recorded_at <= system_time` and not yet superseded). Without a `system_time`, that means the current, non-superseded rows.
  - Per fact key it returns the latest `published_at`; ties go to the later `recorded_at`, then `id`.
- **Why not `recorded_at`:** backfilled history is recorded today, so comparing `known_at` with it would hide all history from backtests.
- **Source-side revision** (issuer restatement, statistical revision):
  - Stored as a new row with a later `published_at`, `restated_flag = true`, `supersedes_fact_id` pointing to the prior row and `revision_reason` set to `restatement` or `revision`.
  - The prior row is not superseded, so an earlier `known_at` still returns the original value.
- **Our own correction** (e.g. a parser error):
  - The wrong row gets `superseded_at` (the only permitted UPDATE), and a new row is stored with `revision_reason = correction`.
  - An earlier `system_time` reproduces what this database said before the fix.
- **Unchanged values:** a repeated value (e.g. a prior-year comparative repeated in a later 10-K) is not a new version. Versions must be ingested in publication order; otherwise the repository raises `FactConflictError`. ADR-013 refines how re-read and conflicting values are classified.
- **Date-only publication times** are stored as the end of that day in America/New_York with `published_at_precision = day`, so a backtest never sees a same-day release early. Exact timestamps use precision `exact`.
- **System time comes from the database clock:** triggers set `recorded_at` on insert and `superseded_at` on supersede. Application code cannot backdate either.
- **Known gaps:**
  - A source withdrawing an observation (no replacement value) cannot be represented yet; design a tombstone when a source first needs it.
  - Backtests and signals must record the `(known_at, system_time)` pair they used (Phase 2).

## ADR-013 SEC EDGAR ingestion rules — Accepted (2026-10-05, approved by Steven with the M0.5 plan)
Applies ADR-007 and ADR-012 to SEC data (M0.5). Code: `apps/api/src/autotrading/adapters/sec/`.
- **Publication time is the EDGAR acceptance time, in true UTC.**
  - Checked on 2026-10-05: `acceptanceDateTime` in the submissions JSON is real UTC, not Eastern time labelled as UTC. EDGAR index pages show Eastern time, for example AAPL 8-K 0000320193-26-000018: JSON `2026-07-30T20:30:28.000Z`, index page "2026-07-30 16:30:28". The plan's working assumption ("ET labelled as UTC") was wrong.
  - Acceptances after 17:30 ET get the next business day as filing date (about 20% of filings), so the acceptance time, not the filing date, is when the filing became public.
  - Fallback: an acceptance of exactly `00:00:00Z` is a date-only placeholder (4 of 192,986 filings, old JPM FWPs), and a missing one has no time. Both use the end of the filing date in New York, precision `day` (ADR-012).
  - Every XBRL value takes the acceptance time of the filing (accession) that reported it; `source_url` is that filing's EDGAR index page; `raw_payload_sha256` is the company-facts response.
- **Amendment (2026-10-06, approved by Steven): new filings are timed from their EDGAR headers.**
  - **What happened:** between 02:00 and 12:00 UTC on 2026-10-06, SEC began returning many `acceptanceDateTime` values late by the New York offset: 4 hours for EDT dates, 5 hours for EST dates (the offset applied twice). Not uniformly: in JPMorgan's main file the newest filing was right while its March 2026 filings were 5 hours late; Apple's and Meta's files were late throughout; Microsoft's were right. AAPL 8-K 0000320193-26-000018 now reads `2026-07-31T00:30:28Z`; its index page and its header `<ACCEPTANCE-DATETIME>20260730163028` still say 16:30:28 New York. The database is clean: the 45 filings stored at 02:00 UTC that day match their index pages.
  - **Rule:** the JSON time is no longer trusted for a filing not yet stored (`adapters/sec/acceptance.py`):
    - filings already stored keep their stored time, and facts take the stored time of the filing they cite;
    - every new 10-K, 10-Q or 8-K (and amendments, 8-K12B) takes its time from its `.hdr.sgml` header; a missing header fails the run and nothing is stored;
    - other new forms (424B2, Form 4, ...) are checked the same way, up to 200 per run, newest first; beyond that, or without a header, they are stored date-only (end of the filing day in New York), never early;
    - when a header differs from the JSON, the run records a note (`ingestion_runs.notes`, migration 0011, "Corrected" on Data Health).
  - A sampled check with a bulk correction was tried first and rejected: with rows late and right in one file, it could move right times early.
  - **Placeholder rule widened:** exactly midnight New York (pre-2009 filings, e.g. 130 of Apple's) is also date-only, like `00:00:00Z`. No stored fact cites such a filing; the 2,170 stored pre-2009 filings keep their stored time (append-only).
  - **Cost:** one header request per new filing, about 45 a day (mostly JPMorgan 424B2s). Recorded fixtures (2026-10-05, before the bug) are replayed without headers.
- **Concepts:** `concepts.py` maps 14 metrics to us-gaap concepts in priority order. For each filing and period, the highest-priority concept that filing reports wins, and the concept is stored in `financial_facts.source_concept`.
  - Only concepts with the same meaning are listed. Three fallbacks are wider, and the glossary caveats name them: `LongTermDebtAndCapitalLeaseObligations(Current)` includes finance leases, `PaymentsToAcquireProductiveAssets` includes intangibles, and `AllocatedShareBasedCompensationExpense` is used when `ShareBasedCompensation` is absent.
  - A metric a company does not report stays unavailable and is never approximated. Examples: gross profit for Alphabet, Meta and JPMorgan; operating income and capex for JPMorgan.
  - Only unit-consistent values are read: USD, shares, USD/shares. EPS tagged `pure` is ignored.
- **Total debt is not stored.** Its components are stored as reported: `long_term_debt_noncurrent`, `long_term_debt_current` and `commercial_paper`. Phase 1 derives total debt as a defined, glossary-backed metric.
- **Versions** (refines ADR-012, `domain/facts.py: decide_version`):
  - **Unchanged:** an incoming value equal to the version known at its own publication time. Re-reading a full history after a restatement is therefore not a conflict.
  - **New version:** a later, different value. It is stored as a restatement.
  - **Conflict:** two different values from one publication (one filing, one period), or a new value older than the newest stored version. The batch path stores none of the disagreeing values, keeps the current version and counts the conflict in `ingestion_runs.rows_conflicted`, so the run still succeeds. The single-fact `insert` still raises.
  - **Stock splits:** splits make later filings report different per-share values and share counts for past periods (Alphabet 20-for-1 in 2022, O'Reilly 15-for-1 in 2025). These are stored as restatement versions, as reported. Phase 1 per-share analytics must handle split adjustment explicitly. Resolved by ADR-021 (M1.1): splits are stored and per-share history is split-adjusted on read.
- **Refresh:**
  - **Schedule:** daily at 10:00 SGT (APScheduler cron). `make sec-refresh` queues the same runs manually.
  - **Chain:** a `sec.tickers` run comes first. Its Dramatiq `on_success` callback queues one `sec.company` run per universe equity.
  - **Windows:** the window is part of the idempotency key. A scheduled run uses the Singapore calendar day, so a repeated trigger is skipped. A manual run uses the start of the day to now, so it always runs.
  - **Cost of one refresh:** about 60 requests at no more than 5 per second, roughly 30 seconds in total. Every run fetches all filing pages; JPMorgan alone lists about 168k filings, mostly 424B2 note supplements.
  - **Storage:** raw responses are content-addressed, so unchanged pages are stored once. Conditional requests (If-Modified-Since) are a later optimization.
- **Filings index:** every form is stored, append-only, one row per (entity, accession).
- **Identifiers:**
  - `valid_from` is when this platform first saw a ticker/CIK mapping. SEC's ticker file has no history.
  - When a ticker moves to another CIK, its old period is closed.
  - When a company's old ticker disappears from the file, its instrument keeps its identity and gets the new ticker (a rename).
- **XOM:** on 2026-07-01, Exxon Mobil moved under a new holding company (8-K12B), and SEC now maps XOM to ExxonMobil Holdings Corp (CIK 0002115436). The history before the reorganization, under Exxon Mobil Corp (CIK 0000034088), is linked by ADR-014 (M0.5b).

## ADR-014 Successor issuers (entity relationships) — Accepted (2026-10-05, approved by Steven with the M0.5b plan)
Resolves the XOM gap in ADR-013.
- **Context:** after a holding-company reorganization, the listed stock's new issuer files under a new CIK. Its XBRL history starts at the reorganization. Years of history stay under the old issuer, which keeps filing (e.g. debt) but no longer has a ticker.
- **Data model:**
  - `entity_relationships` (migration 0005) links a predecessor entity to its successor with type `successor_issuer`.
  - `effective_at` is when the successor took over: the acceptance time of the successor's 8-K12B (XOM: 2026-07-01 16:36:49 UTC).
  - Each link carries its evidence (accession number and EDGAR index URL).
  - Rows are mutable and audited, like identifiers.
- **Curation:**
  - Links are declared by hand in `config/universe.yaml` under `predecessors:`, with the filing as evidence.
  - The `sec.tickers` job creates the predecessor entity, its CIK identifier and the link.
  - Nothing is inferred automatically.
- **Facts stay with their reporter:**
  - The predecessor's filings and facts are ingested under its own entity. The daily refresh includes linked predecessors.
  - No value is copied or re-attributed.
- **Instrument page merge:**
  - **Precedence:** for each metric, unit and period, the current issuer's value wins and the predecessor's fills the gaps. The page names the predecessor next to every value it supplied.
  - **Issuer at a time:** before `effective_at`, the page names the predecessor as the issuer.
  - **Overlap:** the 11 periods both XOM issuers report (2025-2026) are equal.
- **Limits:** only `successor_issuer` exists. Spin-offs and mergers (where history does not simply continue) need their own types and rules before they are modelled.

## ADR-015 FRED / ALFRED vintages — Accepted (2026-10-06, approved by Steven with the M0.6 plan)
Applies ADR-007 and ADR-012 to macro series (M0.6). Code: `apps/api/src/autotrading/adapters/fred/`.
- **Storage:**
  - `macro_series` is the registry: series ids from `config/macro_series.yaml`, metadata from FRED. Rows are mutable and audited.
  - `macro_observations` is an append-only bitemporal fact table with key (`series_id`, `observation_date`).
  - Each ALFRED real-time period is a version. A later vintage with a different value is a new version with `revision_reason = revision`. Versioning uses the same `decide_version` / `apply_versions` rules as financial facts.
- **Publication time:**
  - A vintage's `realtime_start` is a date, so the value counts as public from the end of that day in New York (precision `day`, ADR-012). Example: CPI released at 08:30 ET counts as known at 23:59:59 ET.
  - ALFRED's archive starts at a different date per series. Values published before it carry the archive start as their vintage. That is later than the true release, never earlier.
- **Fetching:**
  - Each run reads all vintages: the series record, its vintage dates, then observations over the full real-time range, paged by 100,000.
  - FRED serves at most 2,000 vintage dates per request. Daily market series have 3,000-5,000, so they are read in real-time windows of at most 1,900 vintages.
  - A value that spans two windows comes back once per window. The repeat is classified unchanged, so it is never stored twice.
  - Missing values (`.`) are not stored. A value that disappears is the tombstone gap noted in ADR-012.
- **API key:**
  - FRED accepts the key only as a query parameter. It lives in Settings as a secret.
  - Stored and shown URLs are built without it (`public_url`). Observations link to `https://fred.stlouisfed.org/series/<ID>`.
  - Errors name the public URL and are raised without exception chaining.
  - httpx2/httpcore2 request logging is limited to warnings.
  - Recorded fixtures are checked for the key before the manifest is written.
- **Refresh:** daily at 10:15 SGT, plus `make fred-refresh`. There is one `fred.series` run per enabled series, in the shared refresh window (`ingestion/schedule.py`).
- **Limits:**
  - ICE BofA series (BAMLH0A0HYM2) are limited by ICE licensing to about the last three years on FRED (from 2023-10-06 at first ingest).
  - ICE and Cboe series carry third-party copyright: personal use only (ADR-001).

## ADR-017 Prices: Alpaca feed, feed status, market calendar — Accepted (2026-10-06, approved by Steven with the M0.7 plan)
Applies ADR-004, ADR-006, ADR-007 and ADR-012 to prices (M0.7). Code: `apps/api/src/autotrading/adapters/alpaca/`, `domain/prices.py`, `domain/market_calendar.py`.
- **Provider:**
  - Alpaca Market Data, Basic plan (free), keys from a paper account.
  - Real time is IEX only (one venue). Consolidated (SIP) real-time snapshots are refused (HTTP 403).
  - Historical SIP daily bars are available from 2016, except the last 15 minutes.
  - Behind `PriceProvider` (`domain/prices.py`). Massive is a placeholder that never reports itself configured.
- **Safety:**
  - The client reaches only `data.alpaca.markets`, and only the paths `/v2/stocks/` and `/v1/corporate-actions`. It refuses any other host or path, so no trading, account or order endpoint can be called.
  - It refuses keys starting with `AK` (live accounts).
  - Keys travel as headers; stored URLs and logs never contain them.
  - Rate limit: 3 requests/second (burst 5) against the plan's 200/minute.
- **Feed status (errata E4), per quote shown:**
  - `live_single_venue`: market open and the IEX quote is at most 120 s old. Snapshots are polled every 60 s. Both instrument classes in the universe (equities, ETFs) use this SLA.
  - `stale`: market open and the quote is older; or market closed and the newest quote is more than 5 minutes before the last close.
  - `end_of_day`: market closed; the newest quote is the last session's close.
  - `unavailable`: no key or no data. The API sends no number.
  - `fixture`: recorded test data. Shown with or without a key, with a DEMO DATA banner (ADR-006).
  - Daily closes are `end_of_day` (or `fixture`).
- **Day change:** the IEX last trade against IEX's previous close (one venue on both sides). For a past date: the consolidated close against the previous close on the same split basis.
- **Market calendar:**
  - NYSE regular hours 09:30–16:00 ET; early closes at 13:00.
  - Holidays and early closes for 2026–2028 are in `config/market_calendar.yaml`, copied from nyse.com on 2026-10-06.
  - The file covers dates until 2028-12-31; extend it before then.
- **Storage (migration 0008, TimescaleDB hypertables):**
  - `market_quotes`: append-only observations (errata E1), one per instrument and quote time. Hypertable on `published_at`, 7-day chunks.
  - `price_bars`: bitemporal facts keyed by (instrument, adjustment `raw` or `split`, bar time). Hypertable on `bar_time`, 1-year chunks.
  - Hypertables need the time column in every unique index, so primary keys are (id, time) and `supersedes_id` has no foreign key.
  - Default hypertable indexes are off, so the schema matches the models.
  - Row and TRUNCATE triggers work on hypertables (checked on TimescaleDB 2.30).
- **Publication time:**
  - Raw daily bars count from the end of their New York day (precision `day`, ADR-012).
  - Split-adjusted bars count from when they were fetched (precision `exact`): that basis is what the provider served then.
- **Splits:**
  - A run that sees a split (corporate actions) in its window fetches that symbol's whole split-adjusted history again. Changed closes become new versions (`revision`).
  - Raw bars never change.
- **Point in time:**
  - A past date shows the raw closes known then.
  - The year chart is the split-adjusted series re-based to that day: raw x factor(as-of day) / factor(day), where factor = raw / adjusted.
  - The factor is snapped to the nearest fraction with a denominator up to 50 (a split ratio) when within 0.5%, because adjusted closes are rounded to cents. Days with no split since then show exactly their raw close.
- **Schedules:**
  - Snapshots run every minute while the market is open, and for 3 minutes after the close.
  - Daily bars run at 06:30 SGT: the last 21 days, raw and split-adjusted.
  - `make prices-backfill` (once, since 2016) and `make prices-refresh`.
  - Data Health judges Alpaca by market session: a closed market does not make it stale, and the next refresh is the next open.
  - The runs list shows the newest 3 runs per job.
- **Universe:** ETFs in `config/universe.yaml` become instruments of type `etf`. Equities reuse their SEC instrument. Ticker identifiers use the `alpaca` namespace.
- **Known gaps:**
  - IEX is a small share of volume and its spread can be wide. Examples from 2026-10-05: SPY traded 1.09M shares on IEX against 44.9M consolidated; AAPL's IEX quote at the close was 316.31 / 349.69. Prices are always labelled `live_single_venue`.
  - On a split's ex-date, the live IEX day change may compare across the split, because the provider's previous close is not adjusted. This is fixed once corporate actions are stored. Splits are stored since M1.1 (ADR-021); using them for the live day change is still to do.
  - Raw snapshot payloads (about 5–10 KB a minute, about 3 MB a session) have no retention policy yet.
  - Closes are split-adjusted only. Dividends are not added back, so the chart is not total return.

- **Tiers:**
  - A news item keeps its publisher's tier, not GDELT's. `config/news_publishers.yaml` sets:

  - Government domains (.gov) are Tier 1. Every other publisher is Tier 4 (unverified, a lead only) until it is reviewed and added.
  - Official and issuer feeds are Tier 1.

  - Feeds are stripped before anything is stored: `content:encoded` is removed, and every summary (description, summary, Atom content) is cut to a 300-character plain-text snippet. The stored "raw" payload is this metadata-only feed.
  - GDELT returns no text.
  - The database refuses titles over 500 and snippets over 300 characters.
  - Recorded fixtures are the stripped feeds.
- **What GDELT gives:** url, title, the time GDELT first saw the article (`seendate`), domain, language and country. No author, publication time or summary.
- **Storage (migration 0009):**
  - `news_items`: append-only, one row per canonical URL, with full provenance. The first copy seen is kept; later edits by the publisher are not stored.
  - `news_mentions`: append-only links to universe instruments, versioned by `extractor_version`.
  - `data_mode = fixture` marks recorded test data and shows the DEMO DATA banner (ADR-006).
- **Time:**
  - Feeds give the publisher's time (`time_basis = publisher`).
  - GDELT gives its first-seen time (`first_seen`), which is never earlier than publication.
  - Both count as when the item became known (ADR-012). A feed time later than our fetch is capped at the fetch time.
- **Duplicate groups:**
  - The same canonical URL is the same article. Canonical means https, no www/m/amp prefix, no tracking parameters, fragment or trailing slash.
  - Copies of one story join one group when they have the same normalised title, or (from different sites) titles of at least four words whose word sets overlap by at least 0.85 (Jaccard), within 72 hours. The title is normalised by dropping a trailing " | Publisher" or " - Reuters".
  - From one site, only the same URL or an identical title groups. A site's own series of near-identical titles are separate releases: White House orders on Canadian dairy and on motor vehicles (2026-09) overlap by 0.88.
  - Checked on recorded GDELT data: no pair of titles from different sites fell between 0.5 and 0.85, so the threshold decides little. Exact copies dominate: one Nvidia buyback headline was carried by 33 sites.
  - A new article joins the most similar group, or the earliest on a tie. The group is set at insert and never changes.
  - Inserts are serialised with an advisory lock, so concurrent runs cannot split a story.
  - Counts are stories (groups), not articles.
- **Company mentions (no language model, ADR-009):**
  - Titles only.
  - Rules and confidence:
    - exchange-qualified ticker (`$NVDA`, `NASDAQ: AAPL`): 1.0
    - issuer feed: 1.0
    - company name or alias (case-sensitive, whole word): 0.8
    - bare upper-case ticker: 0.7. Not used for LOW, an ordinary word.
  - 0.8 and 0.7 are rule weights, not yet measured.
  - Names are the configured aliases plus the SEC name without legal suffixes, when it is in mixed case.
  - GDELT articles are stored only when the title names a universe company. Others are logged as skipped. ETFs are not queried.
- **Schedules:** `ingestion/schedule.py`.
  - GDELT runs hourly at :20 (UTC), searching the last 24 hours.
  - Feeds run every 30 minutes at :05 and :35, with If-Modified-Since.
  - `make news-refresh`; `make news-backfill` (GDELT, one run per day over 14 days).
  - GDELT is limited to one request every 10 seconds, and 429 answers are retried with backoff.
  - When GDELT keeps refusing, a run stops and keeps the equities it already has. It fails only when it got nothing. The next hourly run searches the same 24 hours again, starting from another equity (it rotates by hour).
- **Display:**
  - Headlines and summaries are the publishers' own words, shown verbatim and marked `[data-quoted]`, so the "every number is explained" check skips them. Every number of ours is still a `<Metric>`.
  - The News page and the instrument page's Recent news were pulled forward from M0.9 (minimal).
  - Issuer newsrooms are mostly product and marketing posts (Google's blog: teacher stories; NVIDIA's: game lists next to a USD 150 billion buyback). They are all kept, but shown apart (Steven, 2026-10-06): the instrument page has two columns, "Media coverage" (article, official) and "Company announcements" (press_release), and the News page filters by type (`kind`).
  - WordPress feed footers ("The post ... appeared first on ...") are dropped from summaries.
- **Tests and CI:**
  - Fixtures (`tests/fixtures/news`, about 0.8 MB): GDELT for 2026-09-29 to 2026-10-02 (where its index ended) and the nine stripped feeds. GDELT refused JPM, LOW, MSFT and ORLY throughout the recording (429), so six equities are recorded; `manifest.json` lists the missing ones. Re-record with `uv run python -m tests.fixtures.news.record` (resumable; `--feeds-only` keeps the GDELT files).
  - CI starts the stack with `SCHEDULED_INGESTION=false`: the scheduler then runs only its heartbeat. The news sources need no credentials, so a scheduled run would otherwise fetch live data in the middle of the tests.
- **Known gaps:**
  - GDELT lagged about four days on 2026-10-06: its newest article was from 2026-10-02 10:45 UTC. Freshness then shows the age of the newest item.
  - GDELT throttles hard and seems to count per network address: on 2026-10-06 it answered 429 to the first request of the day and kept refusing for more than 30 minutes, well below one request per 5 seconds. From this network GDELT can be unavailable for long stretches; Data Health then shows it Failing or Stale, and the official feeds carry on.
  - Name matching can mismatch or miss companies named only in the text. In a random sample of 25 kept GDELT titles (2026-10-06), 22 were about the company and 3 only mentioned it ("Google" in a crime report, "a Google moment", "Facebook posts" in a court case). Language-model linking is Phase 3 (ADR-009).
  - Most GDELT publishers are unclassified: of 139 kept articles, 133 were Tier 4.
  - Rewritten stories with different headlines are not grouped, and groups are never merged later. One event can therefore be several stories: NVIDIA's buyback on 2026-09-28 is its press release, 33 copies of one syndicated headline and 5 copies of another. Linking them is event clustering (Phase 3).

- **Price (errata E4):**

  - Only a close stored as `end_of_day` feeds a valuation. A fixture or demo close, a close more than 5 calendar days before T (stale), or no close: every value is Data unavailable, and the reason is given once.

- **Shares (V2):**

- **TTM flows** are the last four quarters (ADR-021): revenue, EBITDA (operating income + D&A) and FCF (OCF − capex). EBITDA is unavailable without operating income (JPMorgan, ExxonMobil) or D&A (Microsoft, Alphabet; V3).
- **TTM diluted EPS (V1):**

  - Right after a 10-K, the fiscal-year EPS alone.

- **Multiples:**

- **Quarters (refines ADR-021):** year-to-date lengths now also cover AutoZone's 12/12/12/16-week year (single quarter 80–100 days, two 160–196, three 245–287).

## ADR-023 Fair value models and assumption versions — Accepted (2026-10-07, approved by Steven with the M1.3 plan)
M1.3a. Code: `domain/fair_value.py`, `api/fair_value.py`, migration 0014. Model output, not fact (02 §32.2): every result is labelled so, and names its method, assumption version, model date and data dates.
- **Decisions (Steven, 2026-10-07):**
  - F1 Enterprise DCF: discount free cash flow to an enterprise value, subtract net debt (ADR-022), divide by shares outstanding (ADR-022 V2, on the valuation price's split basis).
  - F2 Owner free cash flow subtracts SBC: operating cash flow − capex − stock-based compensation, the last four quarters (ADR-021). An assumption version can leave SBC in.
  - F3 One neutral default for all ten companies, labelled "not reviewed": growth bear 0%, base 5%, bull 10% for years 1–5; years 6–10 fade linearly to a terminal growth of 2.5%; equity risk premium 5%. It lives in code (version `default`), not in the database.
  - F4 Assumptions are edited in a form on the instrument page. Each save is a new version with a one-line reason. This is the platform's first write: localhost only (the ports are bound to 127.0.0.1), append-only, audited.
- **DCF:**
  - Discount rate r = the latest 10-year Treasury yield (FRED DGS10) public at T + the equity risk premium.
  - Two stages, annual, discounted at year end: years 1–5 grow at the scenario rate g; years 6–10 fade linearly from g to the terminal rate gT; terminal value at year 10 = FCF10 × (1 + gT) / (r − gT).
  - Bear, base and bull differ only in g. Not meaningful when owner FCF ≤ 0. Unavailable when an input is missing (the missing part is named) or when gT is less than one point below r.
  - Exact decimal arithmetic (precision 40); values per share rounded to cents.
- **Against the price:** implied upside = base / price − 1; margin of safety = (base − price) / base. The price is the M1.2 valuation price; with a fixture, demo, stale or no close both are Data unavailable, and the DCF still shows.
- **Reverse DCF:** the g that makes the base value equal the price, all else unchanged; bisection between −50% and +100% a year, to 0.01 point.
- **Relative valuation:** the six M1.2 multiples at the end of every month since January 2016, each from the fact versions, closes and splits public at that month end (all versions loaded once and replayed in memory). Shows the current value (as on the Valuation block), the history's median, the current value's percentile (share of month ends at or below it) and the number of month ends.
- **Assumption versions:**
  - Table `valuation_assumptions`: instrument, version (from 1 per company), parameters (JSON), reason, author, created_at; unique (instrument, version); append-only and truncate-proof triggers; audited on insert (actor `web`).
  - Parameters are validated: premium 2–10%, terminal growth −2–5%, growth −20–40%, bear ≤ base ≤ bull, at most two decimals, no other fields. Invalid input returns 422 with the rule.
  - `GET /instruments/{ticker}/fair-value?known_at=&assumptions=` (a version number or `default`). Without `assumptions`, it uses the latest version saved by T, so a past date shows what the model said then.
  - `GET`/`POST /instruments/{ticker}/assumptions`: list the versions; save a new one.
- **Reproducibility:** the output depends only on what was public at T and on the version, so the same pair gives the same numbers (integration test: identical after a later restatement and a later version).
- **Live check 2026-10-07 (default assumptions):**
  - Discount rate 10.31% (DGS10 5.31% on 2026-10-05 + 5%).
  - Apple: bear $93.30, base $123.76, bull $163.35 vs $333.04; reverse DCF 23.32% a year; P/E 38.19 at the 95th percentile of 129 month ends.
  - Eight of ten have a DCF. JPMorgan has none (no capex, no net debt). ExxonMobil has none with SBC subtracted, because it reports no separate SBC line; an XOM version can leave SBC out.
- **Known limits:**
  - One discount rate, no WACC, no mid-year convention.
  - Banks are not valued by DCF.
  - Relative valuation compares with the company's own history only, not with peers.
  - History starts when the inputs do (Alphabet's EPS from 2019, Apple's FCF from 2018).
  - The default is not a recommendation.

## ADR-024 Research Record and the Fundamental Research dashboard — Accepted (2026-10-09, approved by Steven with the M1.3b plan)
M1.3b. Code: `domain/research.py`, `api/research.py`; web `/dashboards/fundamental-research` and the instrument page's Research Record. The spec (02 §3, §21) names the modules but gives no formulas; these are ours.
- **Decisions (Steven, 2026-10-09):**
  - R1 Form: one sortable table of every universe equity (the dashboard); each company opens its Research Record on the instrument page (TTM + five fiscal years, every value with its inputs and filings).
  - R2 ROIC = NOPAT / average(stockholders' equity + total debt − cash); NOPAT = operating income × (1 − income tax / pretax income).
  - R3 Capital allocation: where free cash flow went (buybacks, dividends, SBC, cash returned / FCF) and the change in diluted shares. Dividends of a period with no dividend figure at all count as 0 and are named, as D4 does for short-term debt. Buyback intensity, net share reduction and funding are M1.4.
  - R4 Dashboard valuation: P/E, EV/EBITDA, FCF yield and the DCF (base, implied upside, reverse growth) with each company's latest assumption version saved by T; no month-end history (that stays on the instrument page).
- **Periods:** the last five fiscal years and the last four quarters (TTM) when they end after the last fiscal year. Opening balances are those of the day before a period starts (the prior fiscal year end; for TTM the quarter end a year earlier, always a reported balance date). Averages are (opening + closing) / 2. Every TTM input must cover the same four quarters.
- **Formulas:**
  | Value | Formula | Not meaningful when |
  |---|---|---|
  | Revenue growth | revenue / revenue a year earlier − 1 | earlier revenue ≤ 0 |
  | Gross, operating, net margin | each / revenue | revenue ≤ 0 |
  | Effective tax rate | income tax / pretax income (a benefit is kept as reported and noted) | pretax ≤ 0 |
  | ROIC | NOPAT / average invested capital | pretax ≤ 0, or either invested capital ≤ 0 |
  | ROE | net income / average equity | either equity ≤ 0 |
  | FCF conversion | (OCF − capex) / net income | net income ≤ 0 |
  | Net debt / EBITDA | net debt at the period end / (operating income + D&A) | EBITDA ≤ 0 (net cash gives a negative ratio) |
  | Cash returned; / FCF | buybacks + dividends; ÷ FCF | FCF ≤ 0 |
  | Diluted share change | diluted shares / a year earlier − 1, both on T's split basis (TTM: latest quarter against the same quarter a year earlier) | — |
- **Missing data (ADR-013):** a missing input leaves the value unavailable with the input named; a missing derived input is explained by its missing part ("not reported: capex", not "free cash flow"). Some dividend figures without the whole period make dividends unavailable, never 0.
- **Dashboard rows** use each company's latest period, so dates differ (shown per row). Sorting is server-side (`?sort=&dir=`); rows without a value sort last.
- **Shared code:** `market_view()` (facts, splits, closes and valuation price at T) and `dcf_snapshot()` now serve `/valuation`, `/fair-value` and `/research`; their outputs did not change (recorded fixtures identical apart from timestamps).

- Splits, closes and dividends carry their market's zone, defaulting to New York, so every US snapshot recomputes identically.

**TW5 Schedule.**
- Files: the TWSE files of a session appear about 05:20 Taipei the next morning and stay until the next session's files replace them. (Corrected 2026-10-27: on 2026-10-26 the files still held 2026-10-22 because 2026-10-23 was a typhoon closure, not because files wait for a business day.)
- Collection: three runs a day, at 07:40, 09:40 and 20:40 SGT, weekends included, each once a day.
- Factors: Taiwan factor snapshots at 09:50 SGT.
- Losses: a session no run catches is lost for good (KI-27). Runs note lost sessions, and the pages count them.

**TW6 Margin dating.** MI_MARGN has no date. It is dated to the run's STOCK_DAY_ALL session and checked by the chain of balances: each 前日餘額 must equal the stored 今日餘額 of the session before.
- A file whose balances all equal the stored ones is "not updated" and is stored later.
- The first file, or one after a lost session, is accepted with confidence 0.9 and checked at the next session.
- Units are lots of 1,000 shares, confirmed because 2330's margin limit equals 25% of its shares in lots.

**TW7 Storage.**
- OHLCV goes in `price_bars` (raw, feed `twse`).
- Migration 0031 adds `exchange_measures`: bitemporal, append-only, audited, one measure per row. It holds:
  - the price change and trade value;
  - the exchange P/E, P/B and dividend yield, with TWSE's basis in `detail`;
  - 13 margin and short measures.
- A blank P/E (a loss) is not stored; the page shows it as not meaningful. BWIBBU_d is stored only when its date and close equal the session's.

**TW8 Dividends.** From TWT48U_ALL, for ex-dates up to the next session:
- cash dividends go to `dividend_events` (TWD per share);
- stock dividends go to `split_events` as `stock_dividend`, with ratio 1 + 配股率 (KI-28: checked against the reference price at the first case);
- rights offerings are noted, not modelled.

**TW9 Reference price check.** TWSE's change is against the session's reference price, so the reference is close − change.
- A reference more than one tick from the previous close less the recorded dividends is a `reference_price_gap`: a capital reduction, a rights offering or a dividend not recorded.
- It is noted at ingest and shown on the page. This stands in for TWT49U and TWTAUU, which are not in the OpenAPI.

**TW10 Factors.**
- Factor definition sets gain `market` (default US) and `percentile_min_observations`; 0.1.0's hash is unchanged. There is exactly one active set per market.
- 0.2.0 (TW): the price measures of 0.1.0 against 0050, on Taipei dates, `stale_after_days` 14 (longer than the 2026 Lunar New Year closure), no fundamentals, percentiles after 12 month ends.
- S3 and S4 keep 0.1.0. The Radar table stays US only.

**TW11 Valuation percentiles.** The P/E, P/B and yield percentiles use the last session of each Taipei month in `exchange_measures`, and are shown from 12 month ends. They are not mixed with the Research Record's SEC-based P/E.

**TW12 Research only.** No strategy, signal, alert, Telegram push, paper portfolio or risk rule reads Taiwan. There is no TWD/USD rate until M3.9. (Amended by ADR-042 SC12: the Taiwan screens' research report is pushed; nothing else.)

**TW13 Pages.**
- `/instruments` gains a Taiwan (TWSE) section.
- `/instruments/{code}` for a TWSE code shows:
  - the close in NT$, the reference price, volume and trade value, and a year of closes on T's split basis;
  - the exchange valuation with percentiles;
  - margin and short balances with usage and 券資比;
  - dividends and reference checks;
  - factors against 0050;
  - flows as "Data unavailable";
  - the attribution: provider, year, datasets, the licence sentence and URL.
- Every block names its file and publication time in Taipei.

**TW14 Glossary.** 18 Taiwan terms with Chinese hints. `beta_252d` and `relative_momentum_*` 0.2.0 name the market's benchmark.

**Out of scope:**
- history before 2026-10-21, institutional flows and foreign ownership (until TWSE consents);
- TPEx;
- Taiwan fundamentals (M3.8);
- the Taiwan regime and TWD/USD (M3.9);
- any Taiwan strategy or position.

## ADR-040 M3.7b: FinMind as a tier 2 source for Taiwan flows and history — Accepted (2026-10-26, Steven approved the provider and its scope; Claude's decisions under ADR-035)
ADR-039 left three gaps: the TWSE OpenAPI serves only the latest session, its history sits behind website queries that need TWSE's consent, and per-stock institutional flows and foreign ownership are not in the OpenAPI at all. On 2026-10-26 Claude read FinMind's terms (Pricing, 使用條款與隱私權政策, 免責聲明與資料授權) and Steven approved it for the flows and for the price history.

**What FinMind allows.** The free anonymous tier (300 requests an hour, no account, no token) permits personal non-commercial use. Every tier requires the attribution 資料來源：FinMind and forbids redistributing the raw data or building a mirror. FinMind states its data comes from official open channels but does not name the source per dataset. The platform is local and closed, so nothing is redistributed.

**TW15 Rate.** `rate_limit_per_second: 0.08`, burst 1: one request every 12.5 seconds, 288 an hour under the cap. The daily run is 22 to 33 requests.

**TW16 Quota.** A 402 (over the cap) or 403 ("ip banned") is never retried. The client starts a 35-minute cooldown shared through Redis, and every later request checks it before connecting, so the ingestion actor's retries burn no quota.

**TW17 Taiwan factor backfill.** `backfill_points` and `session_points` follow the definition set's market and zone: 0050's sessions and Taipei month ends. The US path keeps its defaults, so the stored US snapshots recompute identically. `make twse-factors-backfill`.

**TW18 Revisions.** A session stored for the first time is public at the end of its Taipei day. When a later fetch shows a different value for a session already stored, that row is public at the end of the fetch day in Taipei, strictly later, so it is stored as a revision and the earlier value stays what was known before (as ALFRED vintages).

**TW19 Units.** On the sessions both sources cover, the FinMind values are compared with the stored TWSE ones (close, volume, trades, change, the margin and short measures, P/E, P/B, yield). All equal gives the batch confidence 1.0; any difference gives 0.9 and a run note naming the fields. On 2026-10-21 every field matched (unit test on the recorded files): FinMind's volume is in shares, its margin in lots, like the TWSE files.

**TW20 Ex-dividend results.** From TaiwanStockDividendResult:
- a 息 row is a cash dividend; its amount must reproduce the reference price (before − cash, within one tick), else the row is noted and skipped;
- a 權 row's stated amount is a price drop, not a ratio; the stock dividend ratio is before / reference − 1 (2881 on 2021-09-06: 84.8 / 77.09 − 1 = 10%);
- a 權息 row cannot be split from two prices and is left out with a note.
Cash goes to `dividend_events`, stock dividends to `split_events` (kind stock_dividend, 1 + ratio), both public at the start of the ex-date in Taipei. The history settles KI-28 for the past cases.

**TW21 Source.** `config/sources.yaml` `finmind`: tier 2, `licensed_personal`, daily, 36-hour SLA, the terms URLs and obligations in its note.

**TW22 Client.** One endpoint, `https://api.finmindtrade.com/api/v4/data`, six datasets: TaiwanStockPrice, TaiwanStockMarginPurchaseShortSale, TaiwanStockPER, TaiwanStockDividendResult, TaiwanStockInstitutionalInvestorsBuySell, TaiwanStockShareholding. A response counts only with `status 200`, `msg success` and a data list. The stored `source_url` is the request URL (no token exists).

**TW23 Storage.** Flows and holdings go to `exchange_measures` in long format: `inst_foreign_buy`, `inst_foreign_sell`, `inst_foreign_net` (Foreign_Investor + Foreign_Dealer_Self), `inst_trust_net`, `inst_dealer_net` (Dealer_self + Dealer_Hedging), `inst_total_net`, in shares; `foreign_shares`, `shares_issued` (shares), `foreign_ratio`, `foreign_limit_ratio` (percent). Migration 0032 adds `shares` to the unit CHECK. Prices go to `price_bars` with feed `finmind`; margin and P/E, P/B, yield use the TWSE measure ids. Every row: source finmind, tier 2, Asia/Taipei, the run and payload hash.

**TW24 TWSE primacy.** A session that has a current `twse_openapi` row for a measure or bar is never written by FinMind. FinMind fills the sessions before the first TWSE session (2016 to 2026-10-20) and any later session with no TWSE close (a lost session, KI-27). Flows and holdings have no TWSE rows, so every session is written.

**TW25 Jobs.**
- `finmind.flows`: daily at 21:30 SGT (FinMind publishes the flows about 20:00 and the holdings about 21:00 Taipei), the 11 codes over the last 10 days (revisions), plus closes for codes with a calendar session without a stored close. `make finmind-refresh`.
- `finmind.history`: `make finmind-backfill`, one run per code and dataset (66 runs, about 14 minutes at the rate), 2016-01-01 to 2026-10-20, idempotent.

**TW26 Factor definitions 0.3.0 (TW).** 0.2.0's measures with `dividends_since` and `percentile_since` 2016-01-01; 0.2.0 retired, its content and hash unchanged. The Taiwan universe is backfilled at every 0050 session and Taipei month end since 2016.

**Pages.** The Taiwan instrument page shows the institutional net buying by group (latest session and the last 20 sessions), the foreign holding and limit, each with its FinMind dataset, publication time and the attribution line; the attribution block names both sources. The Data Health page shows `finmind`.

**Out of scope.** TPEx; FinMind for US data; any FinMind dataset beyond the six; paid tiers (Steven decides, not needed: 22 requests a day).

## ADR-041 M3.10: Portfolio Center I, the real holdings ledger and the Today page — Accepted (2026-10-26, Steven approved recording real holdings, their scope and USD as the base currency; Claude's decisions under ADR-035)
Steven asked on 2026-10-26 for the pushes to show on a dashboard and to manage his own portfolio, following five steps (investment policy, security analysis, portfolio construction, rebalancing, performance evaluation). The platform had a paper portfolio only. Steven decided: record his real holdings (manual entry, local only, backed up; no broker connection, no orders), any US listing or TWSE listing plus cash in each currency, and USD as the base currency (US listings in USD, TWSE listings in TWD, DEXTAUS for the conversion). The Portfolio Center has three parts: M3.10 (this ADR: ledger, valuation, Holdings and Today pages), M3.11 (investment policy, rebalancing, custom screens) and M3.12 (performance).

**H1 Ledger.** Migration 0033 `holding_entries`, append-only and audited (actor `web`): kind buy, sell, dividend (cash), deposit, withdrawal, fee or reversal; an account label; the market (US or TW; none for cash); the instrument and symbol; the currency (a CHECK ties US to USD and TW to TWD); the trade date (never after the Taipei date of recording); quantity and price (and an optional fee) for a trade, an amount otherwise; a note. Each kind's fields are one CHECK, and a NULL never passes as positive. A mistake is never edited: a reversal points at one entry (one each, a unique index) and the entry is entered again. There is no order, broker or execution column; requests with unknown fields are refused (422).

**H2 Snapshots.** `holding_snapshots`, append-only: T, system time, the valuation version, the USD total (null without a rate), cash by currency, the rate and the whole valuation document. Daily at 11:12 SGT (after the closes and FRED's DEXTAUS), none before the first entry; `make holdings-snapshot`.

**H3 Valuation 0.1.0** (`domain/holdings.py`, pure; parameters pinned in a unit test).
- An entry counts at T once its trade date has begun in its zone (New York for US listings and USD cash, Taipei for TWSE listings and TWD cash) and it was recorded by S. A reversed entry and its reversal never count from the reversal's system time on, and both count as before for any earlier S.
- Average cost per account and instrument. Buys before sells within a trade date. Fees reduce cash only (never the cost). Splits and stock dividends effective after the trade date and by T scale the quantity.
- Cash per account and currency; a negative balance is flagged, not refused.
- Marks: the last raw close known at T, moved to T's split basis; stale after 5 days (US) or 14 days (TW, up to nine days closed at Lunar New Year); without a close a position counts at its cost and is flagged.
- USD: TWD divided by the last DEXTAUS value known at T (ALFRED vintages); without one the USD total is unavailable (each currency's total still shows); a rate more than 10 days old is flagged. Weights are of the USD total.
- The 24-hour change is the USD total at T less the total at T minus 24 hours (both as recorded now), less the deposits and withdrawals in between, converted at the later rate.

**H4 Apart from research and the paper book.** Only the holdings modules name the ledger (a unit test lists them). No rule, alert, push, radar, factor, journal or risk check reads it; the paper portfolio is unchanged. A held listing outside the research universe has no issuer or SEC identifier, so no research view lists it; Taiwan codes stay out of every rule (ADR-039 TW12).

**H5 Tracked US listings.** The first entry of a US symbol outside the universe creates an instrument of type `other` with an `alpaca` ticker. The daily Alpaca refresh adds bars and splits runs of their own for the tracked symbols, from their earliest trade date, so a symbol Alpaca does not know fails only those runs. Names are not fetched (the Alpaca client reaches market data only).

**H6 Tracked TWSE listings.** The first entry of a TWSE code outside the universe creates an instrument (type `other`, XTAI) with a `twse` ticker. The daily TWSE run carries the held codes as `extra_codes` and stores their closes and ex-rights only (no measure). A code not in STOCK_DAY_ALL is noted (TPEx is not supported). The TWSE OpenAPI has no history: a tracked code's closes start at its first tracked session, and earlier views value it at cost (flagged).

**H7 Exchange rate.** `config/macro_series.yaml` gains DEXTAUS (glossary `macro_twd_usd`), fetched by the daily FRED refresh with every vintage. The H.10 release publishes a week's rates on Mondays, so the rate used is usually 3 to 7 days old; the age shows next to every USD total.

**H8 API.** `GET /holdings?known_at` (positions, cash, totals per currency, the USD total, the change, the rate used and its age, flags, the latest snapshot), `GET /holdings/entries` (newest first, each counted, reversed or a reversal, and the account labels), `POST /holdings/entries` (422 on invalid fields, an unknown symbol format, a future trade date, or a sell that would leave the account short on its date or now; 409 on a race), `POST /holdings/entries/{id}/reverse` (404, 409 when already reversed or a reversal).

**H9 Holdings page** (`/holdings`, System): the summary, flags, positions, cash, totals per currency, the entry form (fields by kind) and the entries with Reverse; As known on reads the past, and the form and Reverse show only when viewing now.

**H10 Today page** (`/`): the holdings card (USD total, change, largest weights, a flag), the alerts pushed to Telegram in the past week and the open alerts, the US and Taiwan sessions, the radar's counts and any enabled source that is stale or failing, above the macro overview. With As known on, only the overview shows. The nav's first System entry is Today.

**H11 Glossary.** 19 terms with Chinese hints (page_today, page_holdings, holding_entry, holding_reversal, holdings_account, holdings_equity, holdings_change, average_cost, unrealized_pnl, realized_pnl, cash_balance, price_mark, fx_rate_used, fx_lag, holding_weight, holding_flag, holdings_snapshot, net_contributions, macro_twd_usd); the computed ones are registered at valuation 0.1.0.

**H12 Privacy.** Holdings stay on this machine: the API binds to localhost, the backups include them, and no push, log line or verify output names a position. Whether a push may ever mention holdings is M3.11's question.

**H13 Verify.** `make holdings-verify` recomputes stored snapshots at their own T and S and must report all identical.

**H14 Later.** M3.11 and M3.12 read the ledger and the snapshots; nothing here anticipates them.

**Out of scope.** Broker connections, imports and any execution path; TPEx and other Asian markets; lot-level (FIFO) cost; taxes; holdings in pushes.

## ADR-042 M3.11: Taiwan listed-stock screens, movers and the daily research report — Accepted (2026-11-04, Steven approved the whole TWSE-listed market, the FinMind scope and ordering by change; Claude's decisions under ADR-035)
Steven described his workflow on 2026-10-26: turn his stock-picking judgement into explicit conditions (a stock above its rising 20-session average with its group strengthening; a breakout from a consolidation on volume; foreign investors and investment trusts buying on several days, never one), check them every day over the market, and get a research report with the names, the conditions they meet, the volume change and the risks; judge nothing when the data is incomplete or not updated; check the conditions on history so they are not too wide; the report is a screening tool, not a buy or sell signal. On 2026-11-04 he decided: the Taiwan screens read every TWSE-listed company, not the 11 research codes; FinMind may serve those companies' prices since 2024 and ex-dividend results once and the candidates' institutional flows daily (at most 150 requests a day in all); and he wants the stocks that change the most, not the biggest. M3.11 is Taiwan only; investment policy and rebalancing move to M3.12, performance to M3.13.

**SC1 Universe (Steven).** Every company of the TWSE company file (t187ap03_L) that trades, depositary receipts (industry 91) left out: 1,087 on 2026-10-22. The 11-code research universe is unchanged; the other companies never enter Instruments, the radar, the factors or any rule, and have no instrument page.

**SC2 Listed companies.** Migration 0034 `listed_companies` (append-only, audited, with provenance): code, short name, industry, listing date and whether the file still lists the company, a row per company and change. The company file is fetched when a universe instrument is missing, when STOCK_DAY_ALL names a four-digit code never seen in it (a new listing; every four-digit code of the recorded files is a company), and on the first slot of each Taipei Monday. The industry names (`config/twse_industries.yaml`) come from joining t187ap03_L and t187ap05_L on the company code; every code met one name.

**SC3 Daily bars.** The TWSE runs store every listed company's raw bar, price change and trade value from the STOCK_DAY_ALL they already fetch, in one batch (about ten statements for 1,100 codes), and the dividends TWT48U_ALL announces for them; no valuation, margin or TW9 note for codes outside the universe.

**SC4 FinMind history (Steven).** TaiwanStockPrice since 2024-01-01 for the listed companies outside the universe and TaiwanStockDividendResult for all, one run per code and dataset under a fixed window (a re-run queues only what has not succeeded), up to the day before the first TWSE session of the listed companies, sent 13 s apart so the worker never holds more than one waiting FinMind run (KI-30). `make finmind-listed-backfill [DATASET=price|dividends]`, about four hours each.

**SC5 Candidates' flows (Steven).** The 21:30 FinMind run adds the latest judged run's new and watched names, then its movers, the universe left out, in runs of at most 20 codes for the institutional flows only, 270 s apart: at most 150 requests a day with the universe's 22.

**SC7 Movers (Steven: change the most).** Liquid stocks (20-session average trade value at least NT$30 million, at least 60 sessions): z1 (the session's return over the standard deviation of the 60 before), z5 (the 5-session return over that deviation times the square root of 5) and the volume ratio (volume over the 20 sessions' average). A mover has |z1| or |z5| of 2.5 or more, or a volume ratio of 3 or more; ordered by the larger |z|. 30 on the page, 10 in the report. The volume ratio is flagged when a stock action over 5% falls in its window.

**SC8 Screens 0.1.0 (Steven's conditions, Claude's thresholds).** Swing Trend: liquid; close above the 20-session average; that average above its value 5 sessions earlier; close above the 60-session average; at least half the industry's liquid stocks above their own 20-session average (judged when the industry has 5 or more). Notes on both (shown, not required, because flows exist only for candidates): foreign investors and investment trusts net buying on at least 3 of the last 5 sessions. Names are ordered by the movers' change.

**SC9 Watch lists.** A name enters the first session it meets a screen and stays on watch until an ending condition holds (Swing Trend: 2 closes in a row below the 20-session average; Range Breakout: a close below the high it broke, moved for later ex-dates), or until it has been on the list 20 judged sessions and no longer meets the screen.

**SC10 Not judged.** Only sessions the stored data names are judged. A stock without the inputs is unavailable, never listed. *Amended 2026-11-05 (screen rules 0.2.0, delivery rules 0.4.0):* also not judged while fewer than 90% of the companies with a bar of the session have 60 sessions of history. The coverage counts only companies that traded in the 5 sessions before, so with the FinMind backfill a quarter done 0.1.0 judged 2026-11-03 from 297 of 1,089 companies and the report was pushed (KI-34). 0.1.0 keeps that one run; 0.2.0 is backfilled from the start.

**SC13 History check (OD-7).** `make screens-backfill [SINCE=]` judges every stored session from the first with 60 sessions before it, each as known at the end of its Taipei day, the watch lists carried, the industry as first known (the company file was first fetched with M3.11); the page shows the stocks meeting each screen per session, the median, the maximum and the share of sessions with none, never returns. `make screens-verify` recomputes the latest runs at their own T and S and must report all identical. Only today's listed companies have history (KI-31).

**SC14 P2-3's scope (Steven).** Factors, the radar and backtests still read each instrument against its own history only. The Taiwan screens order stocks by their change against their own history, and industry breadth counts across an industry's stocks, as Steven's workflow asks (2026-10-26, 2026-11-04).

**SC15 Page.** `/dashboards/opportunity-radar/taiwan-screens`, under the radar (the 15 dashboards are unchanged): the coverage, the movers, each screen's conditions in words from its rule version and hash, its watch list with the numbers and the bar each reading cites (feed, publication time, row id), a session not judged and why, the history check, As known on, TWSE's and FinMind's attribution. A Today card and a radar link; 20 glossary terms with Chinese hints; `twse_price_change` and `twse_reference_price` 0.2.0, `alert_delivery` 0.3.0.

**Out of scope.** US screens and a wider US universe (a membership source is a provider decision); TPEx; intraday data; screens led by institutional flows (the whole market's flows exceed the free tier); returns after the hits (OD-7); investment policy and rebalancing (M3.12); performance (M3.13).
